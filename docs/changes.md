# Что сделано по сравнению с апстримом

Основа форка — `eae9663` апстрима (версия 0.2.3, 22.10.2026). Ниже наши
изменения по порядку, с тем, что проверено на RG52 Mini. Подробности — в
сообщениях коммитов (`git log eae9663..`).

## Совместимость с эмуляторами и падения

### Имя устройства — `077e853`

`deviceName` теперь `"Mali-G52 (malisx2)"`: имя Arm плюс имя драйвера. Эмуляторы,
которые запоминают выбор GPU по имени (PCSX2/ARMSX2, DuckStation, PPSSPP),
различают libmali и malisx2; слово «Mali» осталось для программ, которые его
ищут. Раньше эта правка жила в dArkOS как патч.

### Occlusion-запросы: пул принимается, счёта нет — `0488ddb`

Раньше `vkCreateQueryPool` отказывал всем типам, кроме timestamp, и Dolphin
бросал весь видео-бэкенд («Failed to create query pool») — на malisx2 он не
запускался вообще. Теперь пул создаётся, `vkCmdBeginQuery`/`vkCmdEndQuery`
ничего не записывают, каждый результат — 0 сэмплов, «готово». Для Dolphin это
то же, что выключенные PerfQuery. Программа, которая отсекает объекты по
occlusion-запросам, не нарисует ничего; об этом одна строка в логе. Почему
заглушка, а не подсчёт, — в [decisions.md](decisions.md).

Проверено: Dolphin из dArkOS 1.3 стартует на malisx2 без патчей.

### Проверка границ storage-буферов в вершинных шейдерах (v7) — `80994d9`

Исправляет потерю устройства в Dolphin (ND Demo, на первой отрисовке в EFB):
page fault по адресу «вершинный буфер + 0xFFFFFFF0». Vertex-задание v7 шейдит
весь диапазон индексов [min, max], включая вершины, на которые индексы не
ссылаются; вершинный шейдер Dolphin, разворачивающий линии, читает для них
`input_buffer[vertex_id - 1]` с `vertex_id = 0`. Теперь доступ к SSBO в
вершинных шейдерах на v7 всегда с проверкой границ, и такое чтение даёт нули.
Подробно — в [emulators.md](emulators.md) и [hardware.md](hardware.md).

Проверено: ND Demo и Metroid Prime по 45 с без ошибок драйвера и сбоев GPU
(ND Demo ~41 кадр против ~37 на libmali, замер сессии dArkOS). Цена для
ARMSX2, у которого шейдеры развёртки спрайтов тоже читают SSBO, — меряется.

### Захват заданий: без пустых submit'ов — `3a8c885`

`MALISX2_MEASURE=csf` писал захват и для submit'а без атомов. Такой submit не
увеличивает номер, и его пустой файл затирал захват настоящего — в том числе
захват упавшего submit'а после сбоя GPU. Теперь пустые не пишутся.

## Скорость отрисовки на v7: меньше compute-заданий на отрисовку

Перед Vertex-заданием каждой отрисовки на v7 могут стоять compute-задания:
копия дескрипторов в таблицы стадии и копия uniform-слов в её FAU-блок. Это
лишние задания в цепочке, которые к тому же задерживают вершины (job manager
стартует задания по порядку). Каждая правка — отдельный коммит; сначала —
счётчики, чтобы видеть, откуда задания берутся.

| коммит | правка |

## FPK в проходах с порядком растеризации (27.10.2026)

| коммит | правка |
|---|---|
| `bc3a6d1` | v7: отрисовка с порядком растеризации для цвета (rasterization order attachment access), которая не читает цветовые вложения, может убивать более ранние фрагменты (forward pixel kill); `MALISX2_V7_FPK_ROA=0` — по-старому |

Раньше FPK выключался у любого конвейера с флагом порядка растеризации для
цвета, как в panvk для v10+. ARMSX2 ставит этот флаг на все конвейеры прохода с
feedback loop, в том числе на отрисовки, которые цель не читают. Поэтому
непрозрачные отрисовки в таких проходах FPK теряли.

Флаг задаёт порядок только для чтений цели. Отрисовка, которая из цели ничего
не читает и пишет её целиком, лишь заменяет то, что оставили бы ранние
фрагменты. Чтение цели исключают остальные условия FPK: input attachment,
смешивание с целью, чтение выходов шейдера. FPK и так убивает смешиваемые
фрагменты в любом проходе, через тот же механизм порядка. Фрагменты с
побочными эффектами не убиваются (`allow_forward_pixel_to_be_killed`).

Аппаратные счётчики, ручка в одном бинарнике, 2 раунда в обратном порядке. Сцены
между прогонами немного расходятся, поэтому всё — на растеризованный квад
(FRAG_QUADS_RAST):

| сцена | инструкций | тактов GPU | зашейдировано квадов после раннего ZS |
|---|---|---|---|
| God of War, палуба | −1,6 % | −0,6 % | 93,4 → 93,1 % |
| God of War, сохранение владельца | −2,1 % | −0,3 % | 93,3 → 93,0 % |
| Jak and Daxter, сохранение владельца | −1,6 % | −0,5 % | 86,7 → 86,5 % |

Выигрыш маленький, но одинаковый во всех трёх сценах. На fps он меньше
разброса между раундами. Картинка не изменилась (снимки экрана God of War и
Jak and Daxter).

## AFBC для текстур на v7 (27.10.2026)

| коммит | правка |
|---|---|
| `b511c07` | v7: AFBC и для образов, которые только сэмплируются (текстуры), а не только для цветовых вложений; `MALISX2_V7_AFBC_TEX=0` — по-старому |

Аппаратные счётчики (ручка в одном бинарнике, 2 раунда в обратном порядке):

fps God of War выше во всех четырёх парах прогонов, хотя работа GPU на квад

## FP16 во фрагментных шейдерах (28–29.10.2026)

| коммит | правка |
|---|---|
| `ce57011` | v7: `MALISX2_V7_FP16` — арифметика фрагментного шейдера в 16-битных float там, где ничему не нужны 32 бита (`mali_nir_fs_fp16.c`) |
| `e09815b` | `MALISX2_V7_FP16=1` решает по самому шейдеру, без второй компиляции |
| `579c6a5` | `MALISX2_V7_FP16_LOG=1`: к каждому решению — оценка сбережённых инструкций, форма шейдера до и после прохода, при `MALISX2_V7_FP16=3` — оценки компилятора обеих сборок |
| `2c219dc` | `MALISX2_V7_FP16=1` решает по оценке спаренных операций |

ALU Bifrost делают две 16-битные операции за инструкцию (`FMA.v2f16` и
подобные), а ARMSX2 и Azahar FP16 не просят. Проход понижает точность сам:
32 бита остаются у всего, что по цепочке операций доходит до координат и
других источников текстур, целочисленных и битовых операций, записей в память
и прочих intrinsic, выходов глубины, трафарета и маски, и у цвета для целей
точнее 10 бит на канал; остальная float-арифметика идёт в 16 битах, цвет для
RGBA8, RGB10A2 и 16F уходит в блендинг 16-битным (регистры F16), а
фильтрованные выборки, питающие только 16-битные операции, возвращают 16 бит.
Операции с константами вне диапазона FP16 остаются 32-битными. Выборки из
текстурных буферов (`texelFetch` из `samplerBuffer`) с 16-битным результатом
бэкенд кодирует неверно — GPU fault 0x51 (Castlevania вставала на втором
кадре), поэтому `nir_opt_16bit_tex_image` не используется, а своя свёртка
берёт только фильтрованные выборки из изображений.

FP16 выгоден не каждому шейдеру (преобразования на краях коротких цепочек,
больше живых регистров). Сначала изменённый шейдер компилировался в обоих
вариантах и оставался лучший по оценке компилятора (теперь
`MALISX2_V7_FP16=3`), но это удлиняло компиляцию: предзагрузка 415 конвейеров
Castlevania — 16,9 с вместо 9,5 с. Поэтому при `MALISX2_V7_FP16=1` драйвер
решает по самому шейдеру после прохода и, если FP16 не выгоден, компилирует
копию без прохода.

Первое правило (`e09815b`) оставляло FP16, если 16-битных float-операций не
меньше 8 и втрое больше, чем преобразований между ширинами. Но инструкцию
экономит не 16-битная операция, а пара: скалярная 16-битная операция занимает
столько же, сколько 32-битная, а две, склеенные в `v2f16`, — одну инструкцию.
Теперь (`2c219dc`) драйвер склеивает операции на копии шейдера так же, как
бэкенд (`nir_opt_vectorize`), и считает, на сколько операций стало меньше;
цена — преобразования между ширинами после склейки (32 → 16 бит — одна
инструкция на пару компонентов, после загрузки varying и у констант — ни
одной; 16 → 32 — по одной на компонент). FP16 остаётся, если сбережённых
инструкций хотя бы на одну больше, чем преобразований, и преобразований не
больше 16: у длинных шейдеров Azahar (20–47 преобразований) FP16-сборка
выходила длиннее при любой оценке. Правило подобрано по 579 сравнениям
`MALISX2_V7_FP16=3` в четырёх играх (`MALISX2_V7_FP16_LOG=1`). Такты по оценке
компилятора, сумма по шейдерам против всего FP32:

| Super Mario 3D Land | +0,25 % | −0,07 % | −1,0 % |

не выбирает. Предзагрузка 415 конвейеров Castlevania (2 прогона): 9,6 с без

## Диапазон индексов на GPU (28.10.2026)

| коммит | правка |
|---|---|
| `f56aa78` | v7: наименьший и наибольший индекс отрисовки, рисуемой одним заданием Indexed Vertex, находит GPU: compute-задание scan (по куску в 128 индексов на поток, атомарные min/max) и compute-задание patch (по потоку на отрисовку: место под varying-и в куче батча, Invocation, Offset start, базовое смещение, дескрипторы varying-буферов, адрес позиций; пустая отрисовка — Null-задание); `MALISX2_V7_GPU_INDEX_RANGE=0` — по-старому |
| `ca3352b` | v7: scan читает по 16 байт (8 или 4 индекса) с первой 16-байтной границы |
| `796ca04` | `MALISX2_NO_PIPELINE_CACHE=1`: стадии компилируются заново, для дампов шейдеров |

Индексы отрисовки v7 драйвер читал на CPU при записи команд
(`index_range`), из памяти, которая у ARMSX2 некэшируемая, по чтению из DRAM
на загрузку: 45 % времени драйвера в GS-потоке Jak and Daxter в игре, 8 %
всего потока — а этот поток там узкое место. Драйвер Arm считает диапазон на
GPU: в его цепочке перед заданиями Indexed Vertex каждого прохода идут
compute-задания, которые их заполняют (на момент отправки в заданиях нет ни
числа вершин, ни адреса индексов). Теперь так и у нас, группами до 256
отрисовок батча; panvk делает то же для indirect-отрисовок (libpan
draw_helper.cl). На CPU остаётся запись в 64 байта на отрисовку.

Varying-и таких отрисовок — в куче на каждый слот кучи тайлера: 128 МБ
адресов, физически растёт по 2 МБ, когда GPU пишет дальше. Смещение в ней
обнуляет задание Write Value, когда батч впервые её использует. Группа
закрывается вместе с батчем и на барьере, после которого читаются индексы.
По GPU считаются отрисовки одного инстанса, чей вершинный шейдер не читает
сырое смещение вершины (`gl_VertexIndex`); остальные — как раньше. Доля в
строке статистики: God of War 43–47 % отрисовок (остальные без индексов),
Jak and Daxter 96 %.

Первая версия scan читала по индексу: на God of War, упёртом в GPU, это +3,7 %
инструкций на квад и +1 % времени GPU. Индексы ARMSX2 лежат в поточном буфере
и выровнены только по своему размеру; с чтением по 16 байт от первой границы
— +0,1 % инструкций и −0,3 % времени GPU на квад, в шуме.
