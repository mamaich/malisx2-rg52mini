# Отладка и замеры

## Переменные окружения

| переменная | что делает |
|---|---|
| `MALISX2_MEASURE=<режимы>[,ключ=значение…]` | режимы `timing` (время GPU по проходам и диспатчам), `draws` (и по каждой отрисовке), `csf` (захват отправленных заданий; на job manager — `jm-NNNNNNNN.bin`), `both`, `shaders`; ключи `dir=`, `chunk=`, `ring=`, `start=`, `count=`, `csfmax=`. Каталог `dir=` должен существовать |
| `MALISX2_STATS=<сек>` | раз в столько секунд — строки «malisx2 stats» в логе: submit'ы, отрисовки, проходы, батчи, атомы, вызовы JOB_SUBMIT, ожидания свободного номера атома, задания на отрисовку; на v7 по стадиям — пересборки и обновления таблиц, копии дескрипторов, пересборки FAU (сколько из них только из-за таблиц и сколько блоков оставлено), копии uniform-слов (и сколько из них сделал CPU); на job manager — какие проходы и барьеры («per pass») и ожидания хоста на GPU («host waits»). При уничтожении устройства — итог |
| `MALISX2_JM_BATCH_PASSES=<1–64>` | проходов на батч (по умолчанию 16) |
| `MALISX2_JM_HEAP_SLOTS=<1–32>` | слотов кучи тайлера (по умолчанию 4) |
| `MALISX2_V7_GPU_UBO_COPY=1` | v7: uniform-слова в FAU копирует задание, а не CPU |
| `MALISX2_V7_GPU_DESC_COPY=1` | v7: таблицы дескрипторов без images заполняет задание, а не CPU |
| `MALISX2_V7_AFBC_TEX=0` | v7: текстуры (образы без COLOR_ATTACHMENT) без AFBC, как раньше |
| `MALISX2_V7_AFBC_DEPTH=0` | v7: вложения глубины D32 без AFBC, как раньше |
| `MALISX2_V7_AFBC_FMT=<0–3>` | v7: AFBC и для форматов в порядке BGR, маска: 1 — B8G8R8A8, 2 — RGB565 (R5G6B5 и B5G6R5); 3 (по умолчанию) — оба, 0 — без них, как раньше. У Azahar сжимает кадр 1280×720 и экраны 3DS, у ARMSX2 — его кадр 1280×720 |
| `MALISX2_V7_AFBC_LEVELS=1` | v7: AFBC и для образов с mip-уровнями и слоями (опыт; на Azahar выигрыша нет) |
| `MALISX2_LOG_IMAGES=1` | в лог — каждый созданный образ: формат, размер, уровни, слои, сэмплы, usage, флаги и раскладка (AFBC, u-interleaved, linear) |
| `MALISX2_NO_PIPELINE_CACHE=1` | кэш конвейеров приложения не используется, каждая стадия компилируется заново — для дампов шейдеров (`BIFROST_MESA_DEBUG=shaders`, `MALISX2_MEASURE=shaders`) |
| `MALISX2_NIR_DUMP=<каталог>` | каждый шейдер, который получает компилятор (`pan_shader_compile`), пишется в `<каталог>/<pid>-<номер>.mxnir` вместе с входными данными компиляции — чтобы прогнать компилятор на нём вне устройства. Формат описан у `struct mali_nir_dump` в `src/compiler/mali_compiler.c`; файл читается сборкой malisx2 с тем же Mesa. Каталог должен существовать; при прогретом кэше конвейеров шейдеров нет — вместе с `MALISX2_NO_PIPELINE_CACHE=1` |
| `MALISX2_V7_FP16=<0–3>` | v7: арифметика фрагментных шейдеров в FP16, где ей не нужны 32 бита. 1 — FP16-сборка остаётся по оценке сбережённых инструкций (правило), иначе шейдер компилируется без прохода; 2 — всегда FP16; 3 — обе сборки и лучшая по оценке компилятора; 0 (по умолчанию) — выключено. Свой кэш конвейеров |
| `MALISX2_V7_FP16_LOG=1` | v7: в лог — решение по каждому изменённому фрагментному шейдеру (оценка сбережённых инструкций и преобразований; при 3 — ещё оценки компилятора обеих сборок и форма шейдера до и после прохода) |
| `MALISX2_V7_GPU_INDEX_RANGE=0` | v7: диапазон индексов отрисовок с одним заданием Indexed Vertex ищет CPU при записи команд, а не compute-задания на GPU |
| `MALISX2_V7_IDVS=0` | v7: вершинные шейдеры целиком и пара заданий Vertex + Tiler на отрисовку вместо IDVS (одно задание Indexed Vertex с разделённым шейдером); свой кэш конвейеров |
| `MALISX2_JM_HIER_MASK=<1–255>` | маска уровней иерархии тайлера вместо правила по числу уровней (десятичная: 10 = 0x0a — уровни 32 и 128 пикселей, 130 = 0x82 — 32 и 2048) |
| `MALISX2_V7_FPK_ROA=0` | v7: forward pixel kill выключен у всех конвейеров с порядком растеризации для цвета, как в panvk |
| `BIFROST_MESA_DEBUG=shaderdb` | статистика каждого шейдера v7 (инструкции, кортежи, клаузы, регистры) в stderr; `shaders` — ещё NIR и дизассемблер. Чтобы шейдеры действительно компилировались, нужны `VK_ENABLE_PIPELINE_CACHE=false MESA_SHADER_CACHE_DISABLE=true` |
| `MESA_DEBUG=1`, `MESA_LOG_LEVEL=debug` | отладочный вывод Mesa |

На Android вместо переменных — свойства `debug.malisx2.measure`,
`debug.malisx2.stats`, `debug.malisx2.jm_batch_passes`,
`debug.malisx2.jm_heap_slots`, `debug.malisx2.v7_gpu_ubo_copy`,
`debug.malisx2.v7_gpu_desc_copy`, `debug.malisx2.v7_fpk_roa`,
`debug.malisx2.v7_afbc_tex`.

Чтобы понять, **почему** таблицы и FAU пересобираются, вне репозитория
хранится временная отладка `debug-v7-why.patch` (накладывается поверх
`MALISX2_STATS`): строки «malisx2 why» — сколько пересборок таблиц из-за
нового шейдера (и сколько из них с той же картой дескрипторов), из-за обычных
UBO, из-за смены сетов; сколько пересборок FAU пришлось на смену пайплайна и
при скольких из них шейдер тот же или раскладка FAU та же.

Подводные камни:

- ключи `MALISX2_MEASURE` пишутся слитно: `csfmax`, а не `csf_max`. Неизвестный
  ключ выключает измерения целиком, в логе одна строка «measurement off: cannot
  parse»;
- в dArkOS игры из EmulationStation запускаются не из вашего окружения, и
  переменные до драйвера не доходят; для опытов эмулятор запускают
  отдельно (`systemd-run --setenv=…` с той же командой, что у ES).

## Сообщения, которые не означают ошибку

- dmesg: «Stride 72 passed to job_submit isn't supported by the kernel»;
- лог: «context without a JIT zone: the kernel refused MEM_JIT_INIT».

## Как искать причину потери устройства

На примере ND Demo (Dolphin), 26.10.2026.

1. **dmesg** даёт адрес и слот: «Unhandled Page fault in AS0 at VA
   0x7C75FFFF0 … TRANSLATION_FAULT … READ», «error detected from slot 1». Лог
   драйвера даёт атом: «device lost: vertex/tiler/compute atom 1 (submission 6,
   command buffer 0, batch 0)».
2. **Проверить пропущенные вызовы.** Нереализованные точки входа пишут в лог
   «malisx2: vkXxx called (…); call skipped» (или «returning
   VK_ERROR_FEATURE_NOT_PRESENT»). Пропущенная команда может оставить
   состояние драйвера несогласованным. У ND Demo таких вызовов не было.
3. **Захват заданий:** `MALISX2_MEASURE=csf,dir=<каталог>,csfmax=<N>`: атомы
   submit'а и память команд его командных буферов. Номер сбойного submit'а в
   имени файла тот же, что в сообщении о потере устройства (submit'ы без
   атомов не пишутся с `3a8c885`, раньше они затирали настоящий захват).
4. **Декодер захвата** разбирает цепочки атомов и задания v7 (Vertex, Compute,
   Tiler, Write Value, Fragment, Draw, Primitive, таблицы Attribute Buffer и
   Attribute) и с ключом `--fault <адрес>` помечает задания, чьи чтения могут
   дать этот адрес. Он хранится вне репозитория, в инструментах форка
   (`jmdec.py`). Поиск в памяти захвата 64-битного адреса буфера быстро
   показывает, кто на него ссылается (у Attribute Buffer младшие биты адреса
   заняты типом).
5. **Какое задание упало.** Job manager пишет статус в первое слово заголовка
   задания: 1 — выполнено, 0 — не начато. Временная отладка, которая при
   сбое печатает последние задания со статусами, хранится патчем вне
   репозитория (`debug-v7-drawdump-jobring.patch`; в нём же
   `MALISX2_DRAWDUMP=N` — печать дескрипторов первых N отрисовок каждого
   прохода). У ND Demo: compute-задание выполнено, следующее — Vertex без
   атрибутов — нет. Значит, вершинный буфер читал сам шейдер.
6. **Шейдер.** Дальше — исходник шейдера эмулятора (для Dolphin —
   `Source/Core/VideoCommon/VertexShaderGen.cpp`). Адрес «база + 0xFFFFFFF0» —
   это элемент −1, завёрнутый в 32 бита.

## Замер скорости

- **Кадры** считаются по флипам DRM (ftrace `drm_vblank_event_delivered`):
  среднее, p95, p99 и максимум времени кадра на заданном отрезке. Без ввода
  эмуляция детерминирована, и отрезок одинаков для всех вариантов драйвера.
  Перед каждым прогоном SoC остывает ниже 62 °C, варианты чередуются.
- **Время GPU по слотам:** tracepoint kbase `mali/mali_job_slots_event`;
  event = type << 24 | slot << 16, start = 1, stop = 2. Это время атома в
  слоте, включая ожидание, а не работа ядра.
- **Работа GPU — по аппаратным счётчикам** (kinstr_prfcnt, см.
  [hardware.md](hardware.md)): загрузка, такты фрагментов и вершин,
  инструкции, обмен с памятью на кадр.
- **Во что упирается игра** — по чувствительности к частотам: GPU 600 МГц
  вместо 900 и CPU 1608 вместо 2016 (ограничение ставится через 12 с после
  старта игры: лаунчер сбрасывает частоты). Jak and Daxter: −10 % fps от CPU,
  0 от GPU; God of War: −14…−20 % от GPU, −4…−8 % от CPU (27.10.2026).
- **Сравнивать только одинаково собранные варианты.** Сборка образа — LTO +
  PGO ([darkos.md](darkos.md)); отладочная сборка без LTO для сравнения
  скорости не годится. Функции, изменённые после снятия профиля PGO, теряют
  его — это тоже надо учитывать.
- Стенд для ARMSX2 (God of War, Jak and Daxter) и скрипты запуска хранятся вне
  репозитория, в инструментах форка.
